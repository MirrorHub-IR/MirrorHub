## معرفی پروژه

MirrorHub یک برنامهٔ متن‌باز و خودمیزبان مبتنی بر PHP و MySQL/MariaDB برای کشف میرورهای نرم‌افزاری و پایش زیرساخت ارائه‌دهندگان آن‌هاست. این پروژه فهرست عمومی قابل جست‌وجو را با مدیریت ارائه‌دهندگان، بررسی دسترس‌پذیری HTTP، بررسی تازگی Metadata مخزن، دریافت پیشنهاد کاربران و API نسخه‌دار ترکیب می‌کند.

برنامه برای اجرا روی هاست معمولی PHP طراحی شده و در وضعیت فعلی به Composer یا فرایند Build مبتنی بر npm نیاز ندارد.

> **بلوغ پروژه:** MirrorHub در حال توسعه و در مرحلهٔ پیش از نسخهٔ ۱.۰ است. مخزن شامل گردش‌کار خودکار کیفیت، تست‌های دود امنیتی و گردش‌کار CodeQL است. این بررسی‌ها جایگزین تست محیط آزمایشی، یکپارچگی دیتابیس، مرورگر، بازیابی بکاپ و ارزیابی امنیت استقرار واقعی نیستند. یادداشت‌های نسخهٔ اولیه در [docs/releases/v0.1.0.md](docs/releases/v0.1.0.md) قرار دارند؛ وجود آن‌ها به معنی انتشار Release در GitHub نیست.

## امکانات اصلی

- **کشف میرورها:** فهرست قابل جست‌وجو، صفحهٔ دسته‌بندی و ارائه‌دهنده، جزئیات مستقل هر میرور، صفحه‌بندی و فیلتر دسته، پروتکل، وضعیت HTTP و سلامت Metadata.
- **مدیریت ارائه‌دهندگان:** دسته‌های نرم‌افزار و ارائه‌دهنده مستقل هستند. Base URL برای محدودسازی صفحات و فیلترهای ارائه‌دهنده بر اساس زیرمسیر URL استفاده می‌شود.
- **پایش HTTP:** بررسی دوره‌ای میرورهای فعال ارائه‌دهنده از طریق HTTP/HTTPS، تلاش مجدد، مهلت پاسخ و آستانه‌های قابل تنظیم، تاریخچهٔ زمان پاسخ، آمار آپتایم روزانه، رخدادهای قطعی و صفحهٔ وضعیت عمومی.
- **سلامت Metadata مخزن:** پروفایل‌های اختیاری برای Debian/Ubuntu، Alpine، Arch Linux، مخازن RPM و مسیر Metadata سفارشی.
- **قالب تنظیم مخزن:** قالب‌های قابل کپی برای APT، APK، Pacman و RPM در صفحهٔ جزئیات میرور.
- **مشارکت جامعه:** کاربر می‌تواند پیشنهاد میرور ثبت کند. داده‌ها اعتبارسنجی، محدودسازی نرخ و برای بررسی مدیر نگه‌داری می‌شوند؛ هیچ پیشنهادی به‌صورت خودکار میرور را فعال نمی‌کند.
- **API عمومی نسخهٔ ۱:** فهرست و جزئیات میرورها، دسته‌ها، آمار، وضعیت ارائه‌دهنده، تاریخچهٔ بررسی و ثبت پیشنهاد جهت Moderation.
- **OpenAPI:** سند ماشین‌خوان OpenAPI 3.1 و نمونه‌های Shell برای مصرف‌کنندگان API.
- **CMS مبتنی بر Markdown:** ایجاد پیش‌نویس، انتشار، ویرایش و حذف راهنما، اطلاعات SEO، اتصال به دسته و بلوک وضعیت زندهٔ میرورها.
- **پنل مدیریت:** نصب از مرورگر، ورود مدیر، مدیریت دسته و ارائه‌دهنده، میرورها، درخواست‌ها و کاربران، تنظیمات پایش و بکاپ/بازیابی دیتابیس.
- **پشتیبان‌گیری و بازیابی:** قالب JSON و ZIP. برای ZIP افزونهٔ PHP به نام ZipArchive لازم است؛ JSON بدون آن نیز قابل استفاده است. مسیر فایل‌ها، محدودیت اندازه و یکپارچگی SHA-256 هنگام پشتیبان‌گیری و بازیابی بررسی می‌شوند.
- **رابط واکنش‌گرا:** پشتیبانی از محتوای فارسی و راست‌چین، فونت Vazirmatn به‌صورت محلی، صفحات عمومی و مدیریت واکنش‌گرا و سنجش زمان پاسخ HTTP در مرورگر.
- **صفحهٔ Donate و ارتباط:** صفحهٔ قابل تنظیم معرفی پروژه و راه‌های ارتباطی؛ این صفحه درگاه پرداخت یا کیف پول نیست.

## مسیرها و بخش‌های سایت

آدرس پایه بر اساس تنظیم SITE_URL در نصب تعیین می‌شود.

| بخش | مسیر |
| --- | --- |
| خانه | / |
| همهٔ میرورها | /mirrors/ |
| دسته‌بندی‌ها | /categories/ |
| ارائه‌دهندگان | /providers/ |
| وضعیت عمومی | /status/ یا /status.php |
| جست‌وجو | /search.php |
| جزئیات میرور | /mirror.php?slug=SLUG |
| راهنماها | /guides/ و /guides/SLUG |
| Donate و ارتباط | /donate.php |
| API نسخهٔ ۱ | /api/v1/ |
| سند OpenAPI | /api/v1/openapi.json |
| نصب اولیه | /setup.php |

مسیرهای خوانا به Apache با mod_rewrite و فایل .htaccess نیاز دارند. در Nginx یا وب‌سرورهای دیگر باید قواعد معادل Rewrite و محدودیت دسترسی را مدیر سرور تنظیم کند.

## فناوری و پیش‌نیازها

| مؤلفه | نیازمندی / مبنای فعلی |
| --- | --- |
| Runtime | PHP 8.2 یا جدیدتر؛ نسخهٔ 8.2 مبنای فعلی CI است |
| پایگاه داده | MySQL یا MariaDB |
| افزونه‌های ضروری PHP | pdo_mysql، mbstring، fileinfo، curl |
| وب‌سرور | Apache همراه mod_rewrite و پشتیبانی از .htaccess |
| ارتباط | استفاده از HTTPS در استقرار عمومی قویاً توصیه می‌شود |
| بکاپ ZIP | افزونهٔ ZipArchive (اختیاری؛ JSON مستقل است) |
| تست توسعه | PHP CLI؛ نسخهٔ Node.js 22 برای بررسی Syntax جاوااسکریپت |
| وابستگی Build | در برنامهٔ فعلی نیازی به نصب Composer یا npm نیست |

در محیط تولید از دیتابیس اختصاصی و کاربر دیتابیس با حداقل مجوز لازم استفاده کنید. نصب‌کننده در صورت داشتن مجوز تلاش می‌کند دیتابیس هدف را ایجاد کند؛ در هاست اشتراکی معمولاً باید دیتابیس و کاربر را ابتدا در پنل هاست بسازید.

## نصب و راه‌اندازی

راهنمای کامل انگلیسی در [docs/installation.md](docs/installation.md) و راهنمای فارسی در [docs/installation.fa.md](docs/installation.fa.md) قرار دارد.

۱. مخزن را در ریشهٔ وب یا زیرشاخهٔ موردنظر قرار دهید.
۲. یک دیتابیس MySQL/MariaDB و کاربر اختصاصی بسازید یا از کاربری با مجوزهای لازم برای نصب استفاده کنید.
۳. ریشهٔ سایت را باز کنید؛ نصب تازه به‌صورت خودکار به /setup.php منتقل می‌شود.
۴. اطلاعات اتصال دیتابیس، آدرس اصلی سایت (با زیرشاخه‌ای مثل /beta در صورت نیاز) و حساب مدیر جدید را وارد کنید.
۵. برای مدیر رمز یکتا با حداقل ۱۲ نویسه انتخاب کنید.
۶. نصب را تکمیل کنید. نصب‌کننده ساختار دیتابیس را آماده می‌کند، تنظیمات محلی محرمانه را می‌نویسد، وضعیت نصب را ثبت می‌کند و مدیر را وارد پنل می‌کند.
۷. اگر هاست نتوانست setup.php را خودکار حذف کند، پس از اطمینان از نصب موفق آن را از ریشهٔ وب حذف کنید. فایل .mirrorhub-installed و config.local.php باید خصوصی بمانند.
۸. وارد /admin/ شوید، دسته‌های نرم‌افزار و ارائه‌دهنده را تنظیم کنید، میرورها را اضافه کنید و تنظیمات پایش را بررسی کنید.
۹. برای پایش تولیدی Cron واقعی سرور تنظیم کنید. اجرای جایگزین با ترافیک کاربران نباید زمان‌بند اصلی محیط تولید باشد.

فایل config.local.php، رمز دیتابیس، توکن ربات، کلید Cron، فایل بکاپ، فایل‌های runtime و لاگ‌های تولیدی را Commit نکنید.

### تنظیمات

ابتدا متغیرهای محیطی خوانده می‌شوند و سپس فایل خصوصی config.local.php. از [config.local.example.php](config.local.example.php) به‌عنوان الگو استفاده کنید؛ اطلاعات واقعی تولید را در آن قرار ندهید.

تنظیمات شناخته‌شده:

- MIRRORHUB_DB_HOST
- MIRRORHUB_DB_PORT
- MIRRORHUB_DB_NAME
- MIRRORHUB_DB_USER
- MIRRORHUB_DB_PASS
- MIRRORHUB_DB_CHARSET
- MIRRORHUB_SITE_URL
- MIRRORHUB_ENVIRONMENT
- MIRRORHUB_MONITOR_CRON_KEY

متغیرهای محیطی بر مقادیر فایل محلی اولویت دارند. اگر برنامه در زیرشاخه نصب می‌شود، آدرس سایت باید همان زیرشاخه را نیز شامل شود.

## سامانهٔ پایش

MirrorHub دو نوع سنجش متفاوت را عمداً از هم جدا می‌کند:

۱. **دسترس‌پذیری HTTP:** بررسی می‌کند که میرور فعالِ متعلق به ارائه‌دهنده از طریق HTTP یا HTTPS پاسخ می‌دهد یا خیر. زمان پاسخ، وضعیت، تاریخچه، آپتایم و رخدادها ذخیره می‌شوند.
۲. **سلامت Metadata مخزن:** فایل Metadata انتخاب‌شده یا شاخص‌های تازگی آن را جداگانه بررسی می‌کند. پروفایل‌های فعلی شامل Debian InRelease، Ubuntu InRelease، Alpine APKINDEX.tar.gz، Arch core.db، RPM repodata/repomd.xml و مسیر نسبی سفارشی هستند.

فقط میرورهای فعال که به حداقل یک دستهٔ نوع provider متصل باشند وارد چرخهٔ پایش دوره‌ای می‌شوند. نوع واقعی URL تعیین می‌کند که آدرس HTTP است یا HTTPS؛ فیلد متادیتای پروتکل به‌تنهایی معیار قطعی نیست.

**محدودیت امنیتی مهم:** پاسخ موفق HTTP یا تازگی زمان Metadata اثبات نمی‌کند که مخزن کامل است، hash تمام بسته‌ها صحیح است یا امضای GPG از نظر رمزنگاری تأیید شده است. بررسی فعلی سلامت مخزن اعتبارسنجی کامل امضای GPG را انجام نمی‌دهد. بررسی عادی امضا و hash در Package Manager توزیع را غیرفعال نکنید.

برای زمان‌بندی سرور، از دستور Cron تولیدشده در صفحهٔ مدیریت پایش استفاده کنید. جزئیات در [docs/monitoring.md](docs/monitoring.md) آمده است.

## API عمومی نسخهٔ ۱

API نسخه‌دار زیر مسیر /api/v1/ قرار دارد. درخواست‌های خواندنی عمومی به API Key نیاز ندارند.

| متد | Endpoint | کاربرد |
| --- | --- | --- |
| GET | /mirrors | جست‌وجو و صفحه‌بندی میرورها |
| GET | /mirrors/{slug} | دریافت میرور فعال |
| GET | /categories | فهرست دسته‌ها |
| GET | /stats | آمار عمومی |
| GET | /status | وضعیت ارائه‌دهندگان |
| GET | /status/{slug}/history | تاریخچهٔ بررسی و آپتایم |
| POST | /contributions | پیشنهاد میرور برای بررسی مدیر |
| GET | /openapi.json | دریافت سند OpenAPI 3.1 |

نمونه درخواست؛ آدرس پایه را برای نصب خودتان تغییر دهید:

~~~sh
API_BASE="https://mirrorhub.ir/beta/api/v1"
curl --fail --silent --show-error "$API_BASE/mirrors?per_page=10"
curl --fail --silent --show-error "$API_BASE/mirrors?q=debian&protocol=https"
curl --fail --silent --show-error "$API_BASE/categories?type=software"
curl --fail --silent --show-error "$API_BASE/status"
curl --fail --silent --show-error "$API_BASE/openapi.json"
~~~

آدرس mirrorhub.ir/beta نمونهٔ نصبی است که در مستندات فعلی آمده؛ وجود این آدرس به معنی تضمین فعال‌بودن Demo میزبانی‌شده نیست.

Endpoint ثبت پیشنهاد، فقط یک درخواست Pending ایجاد می‌کند و میرور را منتشر یا فعال نمی‌کند. مستندات فعلی API سقف ۸ تلاش ثبت پیشنهاد در هر ساعت برای هر IP و حداکثر ۱۰ URL در هر درخواست را تعریف می‌کنند. قرارداد کامل در [docs/api-v1.md](docs/api-v1.md) و نمونه‌ها در [examples/api-v1.sh](examples/api-v1.sh) هستند.

## پشتیبان‌گیری و بازیابی

ابزار بکاپ پنل مدیریت از آرشیو JSON و ZIP پشتیبانی می‌کند. نسخهٔ فعلی فرمت پشتیبان ۶ است. برای ZIP افزونهٔ ZipArchive لازم است؛ در نبود آن، JSON همچنان در دسترس خواهد بود.

برای فایل‌های Upload، مسیر نسبی، سقف اندازه و تعداد فایل، مجموع حجم، نوع فایل و SHA-256 کنترل می‌شود؛ Symlink و فایل‌های اجرایی سرور وارد بکاپ نمی‌شوند. آرشیو بکاپ ممکن است حاوی اطلاعات خصوصی دیتابیس و اعلان‌ها باشد؛ آن را رمزنگاری یا در محل محدودشده نگهداری کنید. دانلود موفق آرشیو اثبات نمی‌کند که بازیابی موفق خواهد بود؛ پیش از اتکا به آن، Restore را در محیط Staging جداگانه آزمایش کنید.

شرح محدودیت‌ها و رفتار بازیابی در بخش بکاپ [docs/admin-guide.md](docs/admin-guide.md) (فارسی) موجود است.

## CMS و راهنماهای Markdown

CMS داخل برنامه قرار دارد و مقاله‌ها را در دیتابیس اصلی ذخیره می‌کند. مدیر می‌تواند مقاله را به‌صورت پیش‌نویس بسازد، منتشر، ویرایش یا حذف کند، اطلاعات SEO را تنظیم کند و آن را به دستهٔ نرم‌افزار یا ارائه‌دهنده متصل کند. صفحات عمومی در مسیر /guides/ نمایش داده می‌شوند.

برای نمایش دادهٔ پایش ذخیره‌شدهٔ یک دستهٔ نرم‌افزار، دستور زیر را در یک خط مستقل مقاله قرار دهید:

~~~text
:::health ubuntu
~~~

به‌جای ubuntu نامک واقعی دستهٔ نرم‌افزار را قرار دهید. وضعیت ذخیره‌شدهٔ میرورها نمایش داده می‌شود و هنگام رندر مقاله بررسی شبکهٔ جدید اجرا نمی‌شود. راهنمای تفصیلی در [docs/markdown-cms.md](docs/markdown-cms.md) (فارسی) قرار دارد.

## پینگ مرورگر

دکمهٔ Ping زمان رفت‌وبرگشت یک درخواست HTTP را از مرورگر کاربر اندازه می‌گیرد. این عملیات ICMP ping و نیز بررسی سروری دسترس‌پذیری نیست. سیاست مرورگر، Mixed Content، DNS، TLS، شبکه و افزونه‌ها ممکن است نتیجه را تغییر دهند؛ بنابراین فقط یک سنجش کمکی است، نه معیار قطعی سلامت ارائه‌دهنده.

## مدل امنیت و گزارش مسئولانه

در کد فعلی این کنترل‌ها دیده می‌شوند:

- استفاده از PDO و Prepared Statement برای دسترسی پایگاه داده و ورودی‌های درخواست.
- توکن CSRF برای عملیات تغییر‌دهندهٔ وضعیت در فرم‌های مرورگر.
- Hash کردن رمز مدیر و بازتولید شناسهٔ Session در جریان نصب/ورود.
- تنظیمات سخت‌گیرانهٔ Session، از جمله HTTP-only و SameSite.
- نگهداری اعتبارنامه‌های دیتابیس و کلید Cron در متغیرهای محیطی یا فایل محلی خصوصی.
- اعتبارسنجی سمت سرور و Escape خروجی متناسب با Context.
- محدودسازی نرخ پیشنهادها با HMAC و بررسی دستی مدیر.
- پاک‌سازی SVGهای آپلودشده برای آیکون دسته‌ها.
- اعتبارسنجی مسیر، نوع، اندازه و یکپارچگی فایل‌های Backup.
- محدودسازی دسترسی Apache به فایل‌های محلی حساس و نشانگر نصب.

این فهرست توضیح کنترل‌های پیاده‌سازی‌شده است و تضمین نبود آسیب‌پذیری نیست. مدیر استقرار باید PHP، دیتابیس و وب‌سرور را به‌روز نگه دارد، HTTPS را اجباری کند، از بکاپ و Secretها محافظت کند، مجوز پوشهٔ Upload را محدود کند و نصب را در محیط Staging آزمایش کند.

پیش از گزارش آسیب‌پذیری [SECURITY.md](SECURITY.md) را بخوانید. جزئیات Exploit، اطلاعات خصوصی کاربران یا رمزها را در Issue عمومی قرار ندهید.

## توسعه و اجرای تست‌ها

مخزن را دریافت کنید و بررسی‌های متناسب با تغییرات را اجرا کنید. در وضعیت فعلی برای توسعهٔ برنامه نیازی به نصب وابستگی Composer یا npm نیست.

~~~sh
git clone https://github.com/MirrorHub-IR/MirrorHub.git
cd MirrorHub
php -l path/to/file.php
php tests/security-smoke.php
node --check assets/js/app.js
~~~

برای بررسی Syntax همهٔ فایل‌ها:

~~~sh
find . -type f -name '*.php' -not -path './.git/*' -print0 | while IFS= read -r -d '' file; do
  php -l "$file" || exit 1
done
find assets/js -type f -name '*.js' -print0 | while IFS= read -r -d '' file; do
  node --check "$file" || exit 1
done
~~~

گردش‌کار Quality در GitHub، PHP lint، تست دود امنیتی/رگرسیون و بررسی Syntax جاوااسکریپت را اجرا می‌کند. گردش‌کار Semgrep با قواعد امنیتی جامعه، کد را اسکن می‌کند و در صورت پشتیبانی، یافته‌ها را با قالب SARIF به GitHub Code Scanning می‌فرستد. Dependabot وابستگی‌های GitHub Actions را هفتگی بررسی می‌کند. این گردش‌کارها فعلاً دیتابیس زنده MySQL/MariaDB برای تست یکپارچه یا تست End-to-End مرورگر ایجاد نمی‌کنند.

### فرایند مشارکت در GitHub

۱. پیش از شروع، Issueها و Pull Requestهای موجود را برای جلوگیری از کار تکراری بررسی کنید.
۲. مخزن را Fork و یک شاخهٔ مستقل ایجاد کنید.
۳. تغییرات را متمرکز و قابل بازبینی نگه دارید و تست اضافه کنید یا دلیل نبود تست را توضیح دهید.
۴. مستندات، Migration، پوشش Backup و سازگاری مسیرهای قبلی را به‌روزرسانی کنید.
۵. با استفاده از قالب Pull Request درخواست بررسی ثبت کنید.

## وضعیت و نقشهٔ راه

MirrorHub در مرحلهٔ پیش از ۱.۰ قرار دارد. مخزن فعلی هستهٔ برنامه، نصب‌کننده، API v1، پایش، بکاپ و تست‌های پایه را دارد. برای رسیدن به بلوغ بیشتر، اولویت‌های بعدی عبارت‌اند از:

- تست یکپارچهٔ خودکار روی نسخه‌های پشتیبانی‌شدهٔ MySQL/MariaDB.
- تست End-to-End مرورگر برای گردش‌کارهای عمومی و مدیریت.
- فرایند مستند و تکرارپذیر آزمایش Backup/Restore.
- آزمون سازگاری گسترده‌تر برای نسخه‌های PHP و وب‌سرور.
- افزایش استفادهٔ واقعی، دریافت بازخورد اپراتورها، رسیدگی منظم به Issueها و انتشار نسخه‌های Tagشده.

پروژه ادعای اعتبارسنجی کامل محتوای بسته‌ها یا امضاهای رمزنگاری‌شدهٔ مخازن را ندارد.
