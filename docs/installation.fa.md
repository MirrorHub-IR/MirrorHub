# راهنمای نصب MirrorHub

این راهنما برای استقرار فعلی PHP/MySQL پروژه نوشته شده است. ابتدا روی محیط آزمایشی نصب کنید؛ نصب و بازیابی را برای اولین بار مستقیماً روی سرویس تولیدی انجام ندهید.

## ۱. پیش‌نیازها

- PHP 8.2 یا بالاتر.
- MySQL یا MariaDB.
- افزونه‌های PHP: PDO MySQL، mbstring، fileinfo و curl.
- Apache با mod_rewrite و اجازهٔ استفاده از .htaccess.
- TLS/HTTPS برای نصب عمومی.
- دسترسی لازم برای ساخت جدول‌ها و در نصب تازه، ایجاد دیتابیس طبق روش میزبانی.

گردش‌کار CI نحو PHP 8.2 را بررسی می‌کند. پیکربندی PHP و وب‌سرور میزبان ممکن است با CI فرق داشته باشد.

## ۲. دریافت فایل‌ها

مخزن را کلون کنید یا فایل‌های آن را از GitHub دریافت و در پوشهٔ وب موردنظر قرار دهید:

~~~sh
git clone https://github.com/ahb1390/MirrorHub.git
cd MirrorHub
~~~

اگر پروژه در زیرمسیر سایت نصب می‌شود، برای نمونه /beta، آن را در مقدار SITE_URL لحاظ کنید. پوشه‌های لازم برای آپلود و لاگ باید مطابق مجوزهای میزبان قابل نوشتن باشند، اما مجوز نوشتن عمومی به کل پروژه ندهید.

## ۳. پیکربندی دیتابیس و SITE_URL

فایل نمونه را کپی کنید:

~~~sh
cp config.local.example.php config.local.php
~~~

سپس config.local.php را ویرایش کنید و مقدارهای واقعی DB_HOST، DB_NAME، DB_USER، DB_PASS و SITE_URL را وارد کنید. SITE_URL باید آدرس پایهٔ قابل‌مشاهده از مرورگر باشد؛ نمونه: https://example.com یا https://example.com/beta. فایل config.local.php را commit نکنید و آن را در فایل‌منیجر عمومی یا اسکرین‌شات منتشر نکنید.

می‌توانید به‌جای فایل محلی از متغیرهای محیطی استفاده کنید:

- MIRRORHUB_DB_HOST
- MIRRORHUB_DB_NAME
- MIRRORHUB_DB_USER
- MIRRORHUB_DB_PASS
- MIRRORHUB_DB_CHARSET
- MIRRORHUB_SITE_URL
- MIRRORHUB_ENVIRONMENT
- MIRRORHUB_MONITOR_CRON_KEY

اگر متغیر محیطی مقدار داشته باشد، بر مقدار فایل محلی اولویت دارد.

نصب‌کنندهٔ فعلی تلاش می‌کند دیتابیس را ایجاد و جدول‌های اولیه را بسازد. در برخی هاست‌ها، کاربر دیتابیس مجوز CREATE DATABASE ندارد؛ در این حالت دیتابیس را از پنل میزبان بسازید و مجوزهای لازم را برای نصب فراهم کنید. پس از پایان نصب، دسترسی کاربر runtime را تا حد امکان به نیازهای برنامه محدود کنید.

## ۴. نصب از مرورگر

1. آدرس عمومی /install.php را باز کنید.
2. نام کاربری مدیر را با ۳ تا ۵۰ نویسهٔ مجاز انگلیسی، عدد، نقطه، خط تیره یا زیرخط تعیین کنید.
3. رمز مدیر را حداقل ۱۲ نویسه انتخاب و تأیید کنید.
4. فرم دارای CSRF را ارسال و نتیجه را بررسی کنید.
5. پس از نصب موفق، فایل install.php را حذف کنید یا دسترسی مستقیم آن را در وب‌سرور مسدود کنید.

نصب‌کننده برای دیتابیسی که قبلاً نصب شده است دوباره اجرا نمی‌شود. اگر خطای اتصال می‌بینید، مقدار SITE_URL یا حساب مدیر را تغییر ندهید تا وقتی که تنظیمات اتصال دیتابیس و مجوزها بررسی شده باشند.

## ۵. پیکربندی اولیه

- دسته‌های «نرم‌افزار» و «ارائه‌دهنده» را در پنل بسازید.
- میرورهای نرم‌افزاری را به دسته‌های مناسب متصل کنید.
- فقط میرورهای ارائه‌دهندهٔ فعال را به دسته‌هایی با نوع provider وصل کنید تا وارد چرخهٔ پایش شوند.
- برای هر میرور، پروفایل metadata مطابق ساختار واقعی مخزن انتخاب کنید. مسیرهای نمونهٔ Debian/Ubuntu، Alpine، Arch و RPM ممکن است برای نسخه/معماری خاص آن میرور نیاز به تغییر داشته باشند.
- تنظیمات اعلان و اطلاعات تماس را فقط در پنل امن انجام دهید.

## ۶. Cron برای پایش

در محیط تولید، Cron واقعی سرور را ترجیح دهید. نمونهٔ اجرای ساعتی:

~~~cron
0 * * * * php /path/to/MirrorHub/cron.php >> /path/to/MirrorHub/cron/monitor.log 2>&1
~~~

مسیر PHP و پروژه را با مسیرهای واقعی میزبان جایگزین کنید. بازهٔ Cron باید با فاصلهٔ پایش تنظیم‌شده در پنل هماهنگ باشد. جزئیات، web-cron و هشدارهای بله در [docs/monitoring.md](monitoring.md) آمده است. کلید Cron را در Git یا گزارش عمومی قرار ندهید.

## ۷. بررسی بعد از نصب

- صفحهٔ خانه، جست‌وجو، جزئیات میرور و /status.php را باز کنید.
- بررسی کنید مسیرهای تمیز /guides/ و /api/v1/ روی Apache کار می‌کنند.
- با /api/v1/openapi.json سند OpenAPI را دریافت کنید.
- ثبت پیشنهاد را ابتدا با دادهٔ آزمایشی کنترل کنید و تأیید کنید فقط در صف مدیر قرار می‌گیرد.
- یک بکاپ تهیه و بازیابی آن را در محیط آزمایشی جداگانه امتحان کنید.
- فایل install.php، تنظیمات محرمانه، دسترسی‌های پوشهٔ uploads و خطاهای عمومی را بازبینی کنید.

## عیب‌یابی

- خطای دیتابیس: DB_NAME، DB_USER، DB_PASS، DB_HOST و مجوزهای MySQL/MariaDB را بررسی کنید.
- خطای 404 برای مسیرهای تمیز: mod_rewrite و AllowOverride میزبان را بررسی کنید؛ در صورت استفاده از Nginx، قوانین معادل باید جداگانه تنظیم شوند.
- صفحهٔ وضعیت خالی: ببینید میرور فعال است و به دستهٔ provider متصل شده و Cron واقعاً اجرا می‌شود.
- سلامت metadata «تنظیم نشده»: برای همان میرور پروفایل انتخاب کنید؛ این وضعیت لزوماً به معنی خرابی میرور نیست.
- API ثبت پیشنهاد با 503: وجود جدول‌های مربوط به درخواست و مجوز نوشتن دیتابیس را بررسی کنید؛ جزئیات داخلی از عمد در خروجی عمومی نمایش داده نمی‌شوند.
