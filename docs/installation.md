# MirrorHub Installation and Deployment Guide

MirrorHub includes a browser-based installer. On a fresh deployment, opening the site root redirects to /setup.php; you do not need to create config.local.php manually before starting the wizard.

## Prerequisites

- PHP 8.2 or newer. PHP 8.2 is the current CI baseline.
- MySQL or MariaDB and the PHP pdo_mysql extension.
- PHP extensions used by the application: mbstring, fileinfo, and curl.
- Apache with mod_rewrite and .htaccess support for clean routes.
- HTTPS for public deployments.
- Restricted filesystem permission to create config.local.php in the application root.
- Database privileges to create the application tables and indexes. The installer may also attempt to create the database if the account is permitted to do so.

Nginx and other web servers need equivalent rewrite and access-control rules configured separately.

## Install from a browser

1. Upload or clone the repository into the intended web root or subdirectory.
2. Open the site's base URL. A fresh installation redirects to /setup.php.
3. Enter the MySQL/MariaDB host, port, database name, username, and password.
4. Use the database connection test. The test checks connectivity; the installation step performs the schema setup.
5. Enter the canonical site URL and choose the first administrator username and password. The administrator password must contain at least 12 characters.
6. Start installation. The wizard prepares the core tables, relationships, request/contribution tables, monitoring schema, CMS schema, and installation state.
7. After a successful setup, an administrator session is created and the browser is redirected to /admin/dashboard.php.
8. Confirm that /setup.php is no longer publicly accessible. The installer attempts to delete itself from the deployed host. If filesystem permissions prevent deletion, remove it manually after confirming that installation completed.

## Database privileges

The installer first attempts to connect to the selected database. If the database does not exist, it attempts to create it when the supplied account has sufficient privileges, such as CREATE DATABASE.

On shared hosting, the usual approach is to create the database and its user in the hosting control panel, then enter those credentials in the installer. Do not use the database root password for an ordinary deployment.

The installer is designed for a fresh database or an installation explicitly recorded as incomplete. It rejects an unrelated non-empty database and does not reinitialize an already completed installation. If setup fails partway through, the recorded installation state allows a safe retry.

## Configuration and secrets

After validating the connection, the installer writes database settings to the private config.local.php file. Never commit this file. The repository includes config.local.example.php as a placeholder-only example.

Environment variables take precedence over local-file values. Supported names include:

- MIRRORHUB_DB_HOST
- MIRRORHUB_DB_PORT
- MIRRORHUB_DB_NAME
- MIRRORHUB_DB_USER
- MIRRORHUB_DB_PASS
- MIRRORHUB_DB_CHARSET
- MIRRORHUB_SITE_URL
- MIRRORHUB_ENVIRONMENT
- MIRRORHUB_MONITOR_CRON_KEY

The configured site URL must include its subdirectory. For example, if the application is installed at https://example.com/mirrorhub, set that exact base URL.

After creating the administrator and application schema, MirrorHub records the installation state and attempts to create the .mirrorhub-installed lock marker. The installer also attempts to remove setup.php. If it cannot do so, remove the deployed installer manually. Keep config.local.php and .mirrorhub-installed inaccessible from the public web.

## Post-installation checklist

- Open the home page, search page, mirror details, and /status.php.
- Check /api/v1/openapi.json and a few API v1 read endpoints.
- Create the software and provider categories needed by your deployment.
- Add provider mirrors and configure the repository metadata profile only when you know the correct metadata path.
- Configure a real server cron job using the command generated in Admin → Monitoring.
- Configure optional notification settings without exposing bot tokens or Cron keys.
- Create a database backup and test restoring it in a separate staging environment.
- Keep PHP, MySQL/MariaDB, Apache, and the operating system patched.

## Monitoring scheduler

Production monitoring should use a server scheduler such as cron or the hosting provider's task scheduler. The exact command is generated by the admin monitoring page according to the configured interval.

For a one-hour interval, a typical Unix cron entry looks like this (replace both paths):

~~~cron
0 * * * * php /path/to/MirrorHub/cron.php >> /path/to/MirrorHub/cron/monitor.log 2>&1
~~~

Do not publish the web-cron key. Do not treat visitor-triggered fallback monitoring as a reliable replacement for the server scheduler.

See [docs/monitoring.md](monitoring.md) for provider selection, monitoring thresholds, metadata profiles, notifications, and scheduling behavior.

## Troubleshooting

- **Database connection fails:** verify host, port, database name, username, password, network access, and database grants.
- **Database creation is denied:** create the database in the hosting panel and enter its name in Setup.
- **Configuration cannot be written:** grant narrowly scoped write permission for the application root during setup. Do not make the entire project world-writable.
- **Table or migration creation fails:** review database privileges for table/index/foreign-key creation and the server error log. Do not paste credentials into a public issue.
- **Clean routes return 404:** confirm mod_rewrite is enabled and .htaccess overrides are permitted. Configure equivalent rules separately for Nginx.
- **Setup cannot remove itself:** delete setup.php from the deployed web root manually after confirming successful installation.
- **The site returns 503 after installation:** investigate temporary database connectivity and the existing installation state. Do not rerun setup against a production database as a first troubleshooting step.

## Deployment security

- Use HTTPS and keep TLS certificate validation enabled.
- Keep database credentials and Cron secrets out of Git.
- Keep config.local.php, .mirrorhub-installed, logs, and backups outside public access.
- Use a dedicated database user with minimum required privileges.
- Restrict write access to the upload and configuration paths.
- Back up the database and uploads, store archives securely, and test restore procedures.
- Never disable package-manager signature validation because a mirror appears healthy.
