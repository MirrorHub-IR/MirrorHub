# راهنمای پایش ارائه‌دهندگان MirrorHub

## رفتار پایش

- فقط میرورهای فعال که به دسته‌ای با نوع `provider` متصل شده‌اند پایش می‌شوند؛ لینک‌های نرم‌افزار به‌عنوان سرور ارائه‌دهنده سنجیده نمی‌شوند.
- فاصلهٔ چرخهٔ پایش از پنل مدیریت قابل تنظیم است. مقدار پیش‌فرض یک ساعت است.
- هر چرخه تا سقف «حداکثر ارائه‌دهنده در هر چرخه» بررسی می‌کند. ارائه‌دهنده‌هایی که مدت بیشتری از آخرین بررسی‌شان گذشته در اولویت هستند؛ بنابراین اگر تعداد آن‌ها از سقف یک چرخه بیشتر باشد، نوبت‌ها بین چرخه‌ها می‌چرخد.
- اگر بررسی اول شکست بخورد، یک بار دیگر تلاش می‌شود. آستانهٔ خطاهای متوالی نیز قابل تنظیم است تا اختلال کوتاه باعث اعلام قطعی و هشدار کاذب نشود.
- اعتبارسنجی گواهی TLS همیشه فعال می‌ماند. خطای گواهی باید در محیط پایش حل شود؛ گواهی نامعتبر نباید به‌عنوان اتصال امن پذیرفته شود.
- تاریخچهٔ بررسی‌ها، آمار روزانه و رخدادهای قطعی نگهداری می‌شوند. نگهداری تاریخچه از پنل قابل تنظیم است.

## زمان‌بندی سرور

بازهٔ چرخهٔ پایش از پنل مدیریت → «پایش سرورها» → «فاصلهٔ اجرای واقعی پایش» انتخاب می‌شود. پس از ذخیره، همان بازه در صفحهٔ عمومی وضعیت نمایش داده می‌شود و زمان‌بند زودهنگام نمی‌تواند چرخهٔ واقعی را پیش از موعد اجرا کند.

پنل مدیر دستور پیشنهادی را متناسب با بازهٔ ذخیره‌شده تولید می‌کند. برای نمونه، با بازهٔ یک ساعت:

```cron
0 */1 * * * php /path/to/MirrorHub/cron.php >> /path/to/MirrorHub/cron/monitor.log 2>&1
```

برای بازهٔ ۲۴ ساعت، دستور روزانه می‌شود:

```cron
0 0 * * * php /path/to/MirrorHub/cron.php >> /path/to/MirrorHub/cron/monitor.log 2>&1
```

برای بازه‌های دو یا سه روز و هفت روز نیز cron روزانه اجرا می‌شود؛ برنامه با زمان آخرین چرخه فاصلهٔ انتخاب‌شده را کنترل می‌کند و در روزهای میانی فقط اجرای زمان‌بند را ثبت کرده و چرخه را رد می‌کند. پس از تغییر فاصله در پنل، دستور نمایش داده‌شده را در cPanel جایگزین کنید.

برای web-cron، آدرس امنی را که پنل پایش نمایش می‌دهد در سرویس زمان‌بندی قرار دهید و همان فاصلهٔ انتخاب‌شده را در آن سرویس تنظیم کنید. کلید دسترسی را محرمانه نگه دارید و در مخزن کد یا گزارش عمومی قرار ندهید. لینک «تست این آدرس» اجرای دستی است و چرخه را فوراً اجرا می‌کند.

اگر Cron سرور یا web-cron در دسترس نیست، MirrorHub می‌تواند هنگام بازدید کاربران اجرای جایگزین را امتحان کند؛ این روش را جایگزین cron سرور در محیط تولید نکنید، چون اجرای پس‌زمینه از زمان‌بندی سیستم قابل‌اتکاتر است.

## هشدارهای بله

1. در بله یک ربات بسازید و آن را به گفت‌وگو یا کانال مقصد اضافه کنید؛ برای کانال باید مجوز ارسال پیام داشته باشد.
2. توکن ربات و شناسهٔ مقصد را در پنل «پایش سرورها» ذخیره کنید.
3. روی «ارسال پیام آزمایشی به بله» بزنید و دریافت پیام را بررسی کنید.
4. توکن را فقط در پنل امن وارد کنید. آن را در Git، URL عمومی، اسکرین‌شات یا لاگ قرار ندهید.

ارسال پیام از Bot API بله انجام می‌شود و پاسخ API نیز بررسی می‌شود؛ پاسخ HTTP موفق به‌تنهایی به معنی ارسال موفق پیام نیست. وب‌هوک اختیاری همچنان می‌تواند جداگانه فعال باشد.


## سلامت محتوای مخزن در برابر دسترس‌پذیری HTTP

وضعیت HTTP تنها نشان می‌دهد که آدرس پایه پاسخ می‌دهد؛ سلامت metadata یک بررسی جداگانه است و نتیجهٔ آن آپتایم HTTP را تغییر نمی‌دهد. از مدیریت میرورها، بخش «سلامت محتوای مخزن» را برای هر میرور فعال کنید و پروفایل مناسب را انتخاب کنید.

پروفایل‌های فعلی:
- Debian: `dists/stable/InRelease`
- Ubuntu: `dists/noble/InRelease`
- Alpine: `latest-stable/main/x86_64/APKINDEX.tar.gz`
- Arch Linux: `core/os/x86_64/core.db`
- مخازن RPM: `repodata/repomd.xml`
- مسیر سفارشی: مسیر نسبی فایل و سربرگ `Last-Modified` بررسی می‌شود.

مسیرها نسبت به URL ثبت‌شده برای میرور هستند؛ اگر نسخه یا معماری دیگری ارائه می‌شود، مسیر را اصلاح کنید. حداکثر سن پیش‌فرض metadata برابر ۱۶۸ ساعت است. «سالم» یعنی فایل پاسخ داده و تاریخ قابل‌استخراج در محدودهٔ تعیین‌شده است؛ «قدیمی» یعنی تاریخ از آستانه گذشته یا `Valid-Until` منقضی شده؛ «نامعتبر» معمولاً مسیر نادرست یا ساختار نامطابق را نشان می‌دهد؛ «خطا» یعنی دریافت فایل موفق نبوده؛ «نامشخص» یعنی تاریخ قابل اتکایی برای سنجش تازگی پیدا نشده است.

این بررسی امضای GPG، hash همهٔ بسته‌ها، کامل بودن کل درخت مخزن یا صحت فایل‌های باینری را تأیید نمی‌کند. در پروفایل Debian/Ubuntu تاریخ و `Valid-Until` فایل `InRelease` خوانده می‌شود، اما امضای رمزنگاری‌شده اعتبارسنجی نمی‌شود. برای اطمینان از نصب امن، ابزارهای خود توزیع باید امضا و hash را بررسی کنند. پروفایل «فقط دسترس‌پذیری HTTP» محتوای مخزن را بررسی نمی‌کند.

بکاپ نسخهٔ ۳ تنظیمات و آخرین نتایج سلامت محتوا را نیز ذخیره می‌کند. بکاپ‌های نسخهٔ ۱ و ۲ برای «حفظ اطلاعات فعلی» قابل واردکردن هستند؛ برای جلوگیری از پاک‌شدن داده‌هایی که بکاپ قدیمی ندارد، «جایگزینی کامل» با آن‌ها مجاز نیست.
